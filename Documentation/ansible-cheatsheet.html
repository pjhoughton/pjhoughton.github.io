🤖 Ansible Cheatsheet

Quick reference for Ansible automation and configuration management

A quick reference guide covering common Ansible commands, inventory structure, modules, and key terminology used in automation workflows.

Basic Commands

Description Command
Ping all hosts ansible all -m ping
Run command ansible all -a "uptime"
Use inventory ansible -i inventory.ini all -m ping
Run playbook ansible-playbook site.yml
Check syntax ansible-playbook site.yml --syntax-check
Create Ansible role ansible-galaxy role init roles/my_new_role

Inventory & Variables

Description Example
List inventory ansible-inventory --list -y
Host vars [webserver]
host1 ansible_user=admin
Group vars [webserver:vars]
http_port=80

Playbook Options

Description Command
Run playbook with verbose output ansible-playbook site.yml -v
Extra verbose debug output ansible-playbook site.yml -vvv
Limit to specific host ansible-playbook site.yml --limit web01
Limit to specific group ansible-playbook site.yml --limit webservers
exclude a specific group ansible-playbook site.yml --limit --limit 'all:!windows'
Run only tasks with a tag ansible-playbook site.yml --tags "install"
Skip tagged tasks ansible-playbook site.yml --skip-tags "config"
Dry run/check mode ansible-playbook site.yml --check
Show tasks that would run ansible-playbook site.yml --list-tasks
Show hosts targeted ansible-playbook site.yml --list-hosts

Ansible Vault

Description Command
Create encrypted file ansible-vault create secrets.yml
Edit encrypted file ansible-vault edit secrets.yml
Encrypt existing file ansible-vault encrypt file.yml
Decrypt file ansible-vault decrypt file.yml
Run playbook with vault ansible-playbook site.yml --ask-vault-pass

Debugging & Troubleshooting

Description Command
Print a variable - debug: var=myvar
Print a message - debug: msg="Hello world"
Gather facts ansible all -m setup
Test connection ansible all -m ping
Show module arguments ansible-doc -s copy

Ansible Galaxy & Roles

Ansible Galaxy is the community hub for sharing Ansible content, including roles, collections, and modules. It contains thousands of reusable automation components created by Red Hat, vendors, and the community.
Topic Details
What is a Role? A structured, reusable unit of automation containing tasks, handlers, variables, templates, files, and defaults. Roles help keep playbooks clean, modular, and maintainable.
Role Directory Structure roles/
└── myrole/
    ├── tasks/main.yml
    ├── handlers/main.yml
    ├── vars/main.yml
    ├── defaults/main.yml
    ├── templates/
    ├── files/
    └── meta/main.yml
Create a New Role ansible-galaxy init myrole
Install a Role from Galaxy ansible-galaxy install geerlingguy.nginx
Install Roles from requirements.yml ansible-galaxy install -r requirements.yml
Example requirements.yml - src: geerlingguy.nginx
- src: git+https://github.com/ansible/ansible-examples.git
Search Galaxy ansible-galaxy search nginx
Use a Role in a Playbook - hosts: webservers
  roles:
    - geerlingguy.nginx
Role Dependencies Defined in meta/main.yml to automatically install required roles.
Collections Collections bundle roles, modules, and plugins together.
Install with: ansible-galaxy collection install ansible.posix
Where Galaxy Stores Content ~/.ansible/roles by default, or as configured in ansible.cfg.

Glossary

Term Explanation
Ansible A powerful, agentless automation platform used to configure systems, deploy applications, orchestrate infrastructure, and manage IT environments at scale. It connects to remote systems over SSH or WinRM and executes tasks using simple, human-readable YAML playbooks. Ansible emphasises idempotency, repeatability, and declarative automation, making it ideal for DevOps, cloud provisioning, CI/CD pipelines, and configuration management.
Ansible Control Node The machine from which you run the Ansible CLI tools (ansible-playbook , ansible, ansible-vault and others).
Managed Nodes Also referred to as ‘hosts’, these are the target devices (servers, network appliances or any computer) you aim to manage with Ansible.
Ansible.cfg The main configuration file that controls Ansible's behaviour, defaults, paths, and environment settings.
Inventory file The inventory defines the hosts and groups that Ansible manages, along with variables assigned to them. It can be a static file, such as INI or YAML, or dynamically generated. It determines which systems Ansible will target.
Playbook A YAML file that defines an automation workflow. A playbook contains one or more plays, which specify the target hosts and the tasks to run on them. Playbooks describe what the desired state of a system should be and how Ansible should achieve it.
Play A play defines which hosts Ansible should target and which tasks should run on them. It acts as the link between your inventory and your automation steps.
Tasks A single action Ansible performs, executed using a module, for example apt, copy, or template. Tasks run in order, are designed to be idempotent, and form the building blocks of plays and roles.
Role A reusable, structured bundle of automation containing tasks, handlers, variables, templates, files, and defaults. Roles promote clean, modular organisation and make playbooks easier to maintain and share.
Handler A special task that runs only when notified by another task. Handlers are typically used for actions that should occur only after changes, such as restarting services.
Facts System information automatically gathered by Ansible at the start of a play, including OS details, network interfaces, hardware specs, IP addresses, and environment data. Facts can be used as variables in tasks and templates.
Pre-tasks Tasks that run before roles and main tasks in a play.
Post-tasks Tasks that run after the main tasks and roles in a play.
Become Method Ansible uses to run tasks with elevated privileges, for example sudo.
Variable precedence The order Ansible uses to decide which variable value wins when multiple definitions exist. Highest to lowest generally follows: extra-vars → task vars → block vars → role vars → play vars → host vars → group vars → inventory vars → role defaults.
Execution order The sequence Ansible follows when running automation: ansible.cfg → inventory → playbook → pre-tasks → roles → tasks → post-tasks → handlers.
Idempotent A property of Ansible tasks meaning they can run repeatedly without making changes unless something is actually different. Idempotency ensures safe, predictable automation.
